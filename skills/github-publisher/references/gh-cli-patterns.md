# gh CLI Patterns for specflow

All GitHub operations use the `gh` CLI. These are the exact command patterns
used by `specflow:github-publisher`.

---

## Authentication Check

Before any operation, verify auth:
```bash
gh auth status
```
If not authenticated, STOP and tell the user to run `gh auth login`.

---

## Milestone Operations (Epics)

### List existing milestones
```bash
gh api repos/{owner}/{repo}/milestones --jq '.[].title'
```

### Create milestone
```bash
gh api repos/{owner}/{repo}/milestones \
  --method POST \
  -f title="{epic-name}" \
  -f description="{scope-description}"
```

### Get milestone number by title
```bash
gh api repos/{owner}/{repo}/milestones \
  --jq '.[] | select(.title == "{epic-name}") | .number'
```

## Issue Operations (Features & Tasks)

### Check if issue exists by title
```bash
gh issue list --repo {owner}/{repo} \
  --search "in:title {exact-title}" \
  --label "specflow" \
  --state all \
  --json number,title \
  --limit 10
```

### Create feature issue
```bash
gh issue create --repo {owner}/{repo} \
  --title "{feature-title}" \
  --milestone "{epic-name}" \
  --label "{domain-label},specflow" \
  --body "$(cat <<'BODY'
## Spec Reference
- **Spec §{section}:** {title}

## Description
{description}

## Tasks
{task-checklist}

## Acceptance Criteria
{criteria-checklist}

---
*Generated by specflow*
BODY
)"
```

### Create task sub-issue
```bash
gh issue create --repo {owner}/{repo} \
  --title "CONTRACT-{NNN}: {task-title}" \
  --label "{domain-label},specflow,{effort}" \
  --body "$(cat <<'BODY'
## Spec Traceability
- **EARS:** docs/specflow/ears/{slug}.md
- **Contract:** docs/specflow/contracts/{slug}.md → CONTRACT-{NNN}

## Prompt Contract

### GOAL
{goal}

### CONSTRAINTS
{constraints}

### FORMAT
{format}

### FAILURE CONDITIONS
{failure-conditions}

## Effort: {effort}

## Dependencies
- Blocked by: {blocked-by}
- Blocks: {blocks}

---
*Generated by specflow*
BODY
)"
```

### Link sub-issue to parent (GraphQL — required for reliability)

The `gh issue edit --add-sub-issue` CLI flag is unreliable. Always use the
GraphQL `addSubIssue` mutation instead. This requires node IDs, not issue numbers.

```bash
# Step 1: Get node IDs for both parent and child issues
PARENT_ID=$(gh issue view {parent-number} --repo {owner}/{repo} --json id --jq .id)
CHILD_ID=$(gh issue view {child-number} --repo {owner}/{repo} --json id --jq .id)

# Step 2: Link via GraphQL addSubIssue mutation
gh api graphql -f query='
  mutation($parentId: ID!, $childId: ID!) {
    addSubIssue(input: { issueId: $parentId, subIssueId: $childId }) {
      issue { id title }
      subIssue { id title }
    }
  }
' -f parentId="$PARENT_ID" -f childId="$CHILD_ID"
```

**Important:**
- Both issues must already exist before linking
- Both issues must be in the same repository
- If the child already has a different parent, add `replaceParent: true` to the input
- On success, the response includes both issue titles for verification

## Project Operations

### Add issue to project
```bash
gh project item-add {project-number} \
  --owner {owner} \
  --url "https://github.com/{owner}/{repo}/issues/{issue-number}"
```

### Get project item ID (needed for field updates)
```bash
gh project item-list {project-number} \
  --owner {owner} \
  --format json \
  --jq '.items[] | select(.content.number == {issue-number}) | .id'
```

### Get project field IDs
```bash
gh project field-list {project-number} \
  --owner {owner} \
  --format json
```

### Set project item status (column)
```bash
gh project item-edit \
  --project-id {project-id} \
  --id {item-id} \
  --field-id {status-field-id} \
  --single-select-option-id {column-option-id}
```

## Label Operations

### Ensure label exists
```bash
gh label create "{label-name}" \
  --repo {owner}/{repo} \
  --description "{description}" \
  --color "{hex-color}" \
  --force
```

**Standard specflow labels:**
| Label | Color | Description |
|-------|-------|-------------|
| specflow | 0075ca | Generated by specflow pipeline |
| XS | c5def5 | Effort: < 30 min |
| S | bfd4f2 | Effort: 30 min – 2h |
| M | d4c5f9 | Effort: 2 – 4h |
| L | f9d0c4 | Effort: 4 – 8h |

## Error Handling

### Rate limiting
If `gh` returns HTTP 403 with "rate limit", wait 60 seconds and retry once.

### Not found
If a milestone or issue reference returns 404, log the error and continue.

### Auth failure
If `gh` returns HTTP 401, STOP immediately and tell the user to re-authenticate.

### Partial failure
Continue executing remaining commands. Log all failures in the receipt file.
The publisher is designed to be re-run safely (idempotent).
